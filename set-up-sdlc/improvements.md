# Improvements to set-up-sdlc

Collected while walking the skill through its first real use, on `Org_assist`, starting 17 Nov 2026. Nothing here has been applied to the skill. Everything is to be assessed together at the end of the walkthrough.

## Kasey's suggestions

Improvements Kasey asked for during the walkthrough, newest last.

- **17 Nov 2026 · Introduce flexibility.** The skill's instructions are explicit, so every case it did not anticipate shows up as a gap. Kasey expects many of these and thinks the fix is one review of the skill's language, not a patch for each gap. Until then the agent carries on using its judgement and logs each case below.
- **17 Nov 2026 · Review before the pull request.** Kasey thinks this may change one of the skill's recommended setups. Under the push-once rule, with the up-to-date setting on, every pull request that needs a change costs a replacement and a full CI run, which is expensive when CI runs in the cloud. So the review happens locally before the pull request, fixes happen locally, and on the off chance a pushed pull request still needs changing it is closed and redone. Kasey believed this was already the flow; the template orders it the other way (row 7 below).
- **17 Nov 2026 · The stack table should have room for Zod.** The section guide lists the language, the frameworks, the database, the hosting, the package manager and the full local check. Kasey: Zod might as well be mentioned, because it serves a different purpose from any of those rows.
- **17 Nov 2026 · The stack step should include a discussion of the real choices.** Kasey's example: Next.js against a Vite React app. The guide today asks only "what they plan to use".
- **17 Nov 2026 · A handbook topic for the standard tech stack.** Kasey asked whether `dev-standards-handbook` has a topic the setup could visit, acting as a list of the standard stack and updated as we go. Checked the same day: it has 19 topics and none is a stack list. `frontend-development.md` is deliberately neutral, with rows for Next.js, a Vite React app, TanStack and a single-page application. Zod and Drizzle are assumed throughout `data-integrity.md` and `schema-evolution.md`, and Vitest in `testing.md`. Fastify is not mentioned anywhere.
- **17 Nov 2026 · To add to the skill: never draw on another repo unless asked.** Kasey's instruction, deferred to the end with the rest: the skill needs an explicit rule that the agent does not take facts, settings or a proposal from another repo unless the owner asks it to. It may offer to ("shall I look at how another repo does this?"), but it never just does it. Prompted by row 8 below.
- **18 Nov 2026 · The stack step looks forward, and the result is one table in the agent file.** Kasey thought the forward look at what the product might need (row 10) worked well once it happened, and that the skill could do it by design: the agent suggests what the product is likely to need; the owner rejects what will never be needed; and a rough guide of what is needed and when goes into the repo's agent instructions as a single table, holding what has been decided and what has not. **Applied 18 Nov 2026 on Kasey's word:** `section-guide.md` now describes "the table of what the product needs" in place of "the stack table", with two things he added when he approved the draft: very clear instructions to confirm every suggestion with the user, and a table of suggested triggers for when each need is decided. `AGENTS-example.md` shows the new table and `AGENTS-template.md`'s setup comment names it. Not applied: moving the step ahead of Git and CI/CD in `SKILL.md`. On this repo he agreed the "before anything is built" group, with two changes: repo layout matters most to him, because it is the code's architecture and he is strict about it; sign-in is critical but not needed straight away.
- **18 Nov 2026 · Setup is run once.** Kasey's ruling on review finding 2: he would only ever run `set-up-sdlc` once on a repo. So anything that relies on running it again is wrong, and the later stages of Git and CI/CD (integration, going live and the rest) have to be raised and built by another means. This overturns "Running it again" in `SKILL.md` and the line in `git-and-cicd.md` that says its triggers are not copied into the repo's agent instructions.
- **18 Nov 2026 · Rulings on the other review findings.** Finding 3: yes, change "decided" to "agreed". Finding 9: leave it, it is fine. Finding 10: the order build, review, fix, pull request always holds, but where CI runs is for the user and the agent to settle for each repo, because it depends on the repo's rules. For this repo he wants the checks run during the review and again automatically on the pull request. Finding 4: his reply was one word and the agent is confirming what it meant before acting.
- **18 Nov 2026 · Ownership of pull requests, so none is forgotten.** Something Kasey has wanted to design: each pull request has an owner who is reminded to merge it, and live agents are told when one has a problem, so it cannot be forgotten. Not designed yet. Agreed so far on 18 Nov: (1) the session that opens a pull request watches it to the end. Kasey believes his agents already do this and wants it explicit, so the template and the example now carry "The pull request you open is yours." under the Building table. (2) GitHub's author and assignee fields name the person, and every agent uses Kasey's login, so they cannot tell sessions apart; the ticket does that, through the pane it is pinned to. (3) A scheduled sweep should tell the live agents working in the repo about a red or stale pull request, so catching it does not depend on Kasey's phone. Not built. Kasey's requirements for it, same day: it can be a scheduled Claude Code run; it must be replicable on other people's workstations, so it has to live in this skill; it also goes into the skill's example file; and the skill's template and example are the golden standard, updated as each thing is agreed. He also asked that the ownership instruction sit in a compulsory section, because the Git and CI/CD section is negotiated per repo. It already does: it is fixed text under Building.
- **18 Nov 2026 · A "Scheduled runs" section in the agent file.** Kasey's idea: a new section, discussed as part of setup, listing what runs on a schedule. The pull request sweep is in it and highly recommended, so that pull requests are finished, fixed and watched. Setup can also recommend routine code reviews, routine CI/CD reviews, test suite reviews and anything else needed, especially where several people work on the app. The agent's notes on it: the skill already mentions "regular runs" as a later-stage item in `git-and-cicd.md`, which would need reconciling; "routine reviews" already means the per-change reviews in the house rules, so the names could clash; and a run that belongs to a person (the sweep) should run on each workstation, while a run that belongs to the repo (a code review) should run once, in one place, or every collaborator's machine repeats it. **Applied 18 Nov 2026 on Kasey's word,** with the extra column he asked for ("How it runs": cron or not, local or cloud): a fixed "Scheduled runs" section in the template, a guide entry, a new step 7 in `SKILL.md`, an example section, and two lines in `git-and-cicd.md`. The sweep itself is not built, and the guide says so.
- **18 Nov 2026 · What makes a good row in the table of needs.** On agreeing OrgAssist's 15 waiting needs, Kasey said what he liked about them: none is tied to a feature, and each is a high-level planning item. The guide does not yet say that a need is something the product stands on and never a feature.
- **18 Nov 2026 · Introductory epics.** Kasey: setup creates or confirms the Linear team, but never discusses how to organise the first epics, and without that agents drop tickets in at random. It must stay flexible: near the end, the agent asks the owner which epics fit the build for now and makes sensible suggestions from the conversation it has just had. The agent's view when asked: a good idea, placed at the end, just before setup files its tickets. Suggest only epics for work the setup conversation itself produced, each a coherent outcome with an end and never a category, in line with the `linear` skill's "project = epic" and its ban on holding projects. Leave product epics to the "deciding what to build" route. `git-and-cicd.md` currently puts setup's tickets "under one parent ticket for infrastructure", which would need reconciling with this.

## The agent's view, where Kasey asked for it

- **17 Nov 2026 · The stack step on a repo with nothing built (rows 4, 8, 9 and 10).** Asked whether the instruction needs changing, the agent said yes. The step is written for reading facts off a built repo, and for an unbuilt one it has a single line ("ask what they plan to use"). Its view of what the step needs: (1) start from what the product needs, read from the repo's own documents or asked of the owner, before proposing any tool; (2) sort those needs by when they must be decided, as `git-and-cicd.md` already does for environments, and decide in the sitting only what the hook and CI depend on or what is hard to reverse; (3) put the rest on a ticket; (4) come before Git and CI/CD when nothing is built, since that section needs the answers. Its caution: setup should not become the architecture session. The larger choices belong to the "deciding what to build" route, each with its own decision record.
- **18 Nov 2026 · One table of decided and undecided needs.** Asked what it thought of Kasey's idea above, the agent agreed and preferred it to its own proposal of a ticket. Its reason: every session reads the agent file, so an undecided row tells an agent what it must not choose by itself while building. A ticket is read once. Its cautions: keep each row to the need, its state and what triggers the decision, with the reasoning left to decision records; give a trigger and not a date for "when"; and check the wording nearby. (Corrected the same day: the agent first said the section guide forbids writing "what is planned". That line governs only the opening sentence. The stack table is described as "a table of plain facts", and it is the Git and CI/CD section that says "no list of what might come next". So the table contradicts nothing; the stack table's description simply needs rewriting.)
- **18 Nov 2026 · Repo layout (asked for by Kasey).** After agreeing OrgAssist's layout, Kasey asked where the naming rules came from and whether any of the discussion belongs in the skill. The agent's answer: the naming rule is already in the skill, as the Naming row of the template's house rules, and in his global instructions; the handbook gives only "split by concept, not by technical layer" and "enforce boundaries with a check", and prescribes no folder tree. Nothing in the skill prompts a layout discussion at all: the guide's usual rows do not include it, and "About this repo" says "No map of the folders". The agent's view of what should land: (1) repo layout as a named decide-now need, proposed as a convention before any names; (2) Kasey's layout preferences that hold in every repo as fixed text, so they are not argued afresh each time: feature-based and never layered, a package for code that needs neither the database, the web server nor the browser, one door per feature, no file made just to complete a set, and boundaries enforced by a check; (3) a closed list of role suffixes agreed per repo, since the house rule says the role comes second but not which roles exist. A convention is rules, not a map, so "No map of the folders" can stay. **Applied 18 Nov 2026 on Kasey's word:** a "Layout" row in the template's house rules, a pointer from the Naming row, a "Where code goes" part in "About this repo" (guide entry, example, and a second fixed line in the template), and the boundary check added to what part 4 of `git-and-cicd.md` builds and proves.
